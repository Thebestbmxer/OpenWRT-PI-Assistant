Phase 1 — Router Identity & Persistent Connection 🟡 IN PROGRESS

This is where we are now.

The original Phase 1 has effectively expanded into a more concrete architecture.
1.1 Router device model ✅

Implemented:

Router
├── identity
├── candidate
├── name
├── model
├── architecture
└── target

The important architectural separation is:

Identity
    MAC
    SSH host-key fingerprint

Location
    IP
    SSH port
    interface

This is the correct foundation for DHCP changes and network rediscovery.
1.2 Router identity ✅

Implemented:

RouterIdentity
├── mac_address
└── ssh_host_key_fingerprint

The router's identity is therefore independent of its current IP address.

Tests are passing for:

    stable identity
    identity/location separation

1.3 Router state persistence ✅

Implemented:

RouterState
├── MAC
├── SSH host key
├── IP
├── SSH port
├── username
├── first_seen
└── last_seen

And:

RouterStateRepository
├── save()
└── load()

The repository persists state under the controller's data directory.

Tests verify:

    state can be saved
    state can be loaded
    missing state is handled
    IP changes don't destroy router identity

So this portion is already substantially complete.
1.4 Network discovery ✅

The discovery architecture is now much better than the original "guess an IP" approach.

Current flow:

Pi network interfaces
        │
        ▼
Local IPv4 networks
        │
        ▼
Candidate addresses
        │
        ▼
SSH port check
        │
        ▼
RouterCandidate

Discovery does not authenticate or modify the router.

That's an important separation.
1.5 MAC/neighbor discovery ✅

We've now added the foundation for determining the MAC associated with an IP through the Pi's local neighbor information.

This supports the architecture we discussed earlier:

Current Pi IP/network
        │
        ▼
Determine local network
        │
        ▼
Find router candidate
        │
        ▼
Check neighbor/MAC information
        │
        ▼
Compare with known router

Tests are passing.

1.8 Secure host-key verification 🔴 NEXT

This is the next actual development task.

Currently the permanent SSH connection still has:

AutoAddPolicy()

That isn't acceptable as the final security model.

We need to implement:

Known router
      │
      ▼
Expected host-key fingerprint
      │
      ▼
SSH connection
      │
      ▼
Host key received
      │
      ├── MATCH ───────► CONNECTED
      │
      └── MISMATCH ────► REJECT

This is the point where the router's SSH identity becomes a genuine security control rather than merely information we collect.
Tests to add

At minimum:

    unknown host key handling
    matching fingerprint accepted
    changed fingerprint rejected
    fingerprint stored correctly
    fingerprint survives state persistence
    connection failure on identity mismatch

This is our next coding step.

This will be the real completion of the current milestone.
Phase 2 — Router Information API ⏳

Once we have a reliable connection, we should stop having the UI know anything about SSH commands or OpenWrt internals.

Introduce something like:

Router
 │
 └── RouterInformation
       ├── system()
       ├── network()
       ├── security()
       └── services()

For example:

router.get_system_info()
router.get_network_info()
router.get_security_status()

The UI receives normalized information.
Phase 3 — OpenWrt Integration ⏳

    ├── network.py
    ├── security.py
    ├── services.py
    └── capabilities.py

The core controller shouldn't need to know that OpenWrt uses particular commands/files.

Instead:

Controller

     ▼

     │
     ▼
OpenWrt Integration
     │
     ▼
SSH
