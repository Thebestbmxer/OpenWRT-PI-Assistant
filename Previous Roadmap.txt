System Overview
The project is a Raspberry Pi–assisted OpenWrt platform designed to extend the useful life of very resource-constrained routers such as the WNR1000v2.
The design intentionally separates responsibilities:

                    │  LEDs                    │
                    │  Diagnostics             │
                    └──────────────────────────┘
The router provides the hardware functions while the Pi provides the management, computation, storage, and higher-level networking functions.
The controller software is intended to work with generic OpenWrt installations using supported OpenWrt interfaces. The WNR1000v2 is the eventual constrained target, rather than the definition of the Pi software.
System Intent
The project has four major goals.
1. Extend legacy router hardware
A 4 MB flash / 32 MB RAM router can continue serving as:
managed Ethernet switch
VLAN-aware network device
managed wireless AP
Wi-Fi client
wireless-to-Ethernet adapter
travel-network radio interface
The Pi supplies the computational resources needed for modern networking.
2. Preserve OpenWrt compatibility
The Pi communicates through established OpenWrt mechanisms such as:
SSH
UCI
ubus
netifd
standard Linux networking interfaces
standard wireless interfaces
supported OpenWrt utilities
The project therefore acts as an OpenWrt secondary management layer rather than replacing OpenWrt.
3. Provide a familiar interface
The Pi hosts a locally accessible webpage with an OpenWrt/LuCI-inspired layout and terminology.
The initial GUI is read-only and displays the actual state of the connected router.
Status
System
Network
Wireless
Switch
Diagnostics
Logs
This allows an experienced OpenWrt user to understand the interface immediately.
4. Establish a foundation for constrained firmware
Once the generic Pi controller has been validated against multiple OpenWrt devices, the project produces a purpose-built WNR1000v2 image containing only the functionality required by the controller and hardware.
Router Responsibilities
The eventual 4 MB router image is centered around:
Ethernet
├── managed switch
├── VLAN support
└── Controller Port

Wireless
├── Managed AP
├── Wi-Fi client
└── live Wi-Fi scanning

Management
├── SSH
├── persistent host key
├── Pi controller key
└── OpenWrt configuration

Identity
├── immutable factory MAC
├── configurable operational MAC
├── hardware identity
└── firmware identity

Diagnostics
├── LEDs
├── switch-port state
├── interface statistics
├── Wi-Fi status
├── boot information
└── system health
The Controller Port is always the physical WAN jack.
Its logical function is determined by the deployment:
Home/AP deployment
    Controller Port → upstream/home Ethernet

Travel deployment
    Controller Port → Raspberry Pi
The physical WAN jack therefore becomes a standardized high-speed connection point for the Pi while retaining the flexibility of an ordinary switch port in the logical network design.
MAC Identity
The router maintains two MAC identities:
Factory MAC
    │
    └── immutable hardware identity

Operational MAC
    │
    └── active network identity
Normal home/AP operation uses:
Operational MAC = Factory MAC
Travel mode permits the Pi to configure the operational MAC.
This allows future synthetic/randomized MAC functionality while maintaining predictable physical identities for ordinary home deployments.

The WNR image should be assembled with the OpenWrt ImageBuilder or equivalent supported image-generation process so dependencies are resolved by OpenWrt rather than manually maintained.

The guiding principle is:
Every package earns its place by directly supporting router hardware, OpenWrt management, or the Pi-controller protocol.

The key development strategy is therefore:
Generic OpenWrt first → read-only GUI → device profiles → diagnostics/history → controlled configuration → Pi network services → WNR-specific 4 MB image.
This sequence lets the Pi software mature against a broad pool of existing OpenWrt hardware before the highly constrained WNR1000v2 image becomes the optimization target.
