OpenWrt Pi Controller — System Overview & Roadmap
System Overview

The project is a Raspberry Pi–assisted OpenWrt platform designed to extend the useful life of resource-constrained routers such as the Netgear WNR1000v2.

The architecture intentionally separates responsibilities:

                    ┌──────────────────────────┐
                    │      Raspberry Pi        │
                    │                          │
                    │  OpenWrt Secondary GUI   │
                    │  Device Profile          │
                    │  Configuration History   │
                    │  Firmware Tracking       │
                    │  DHCP / DNS              │
                    │  Firewall / Routing      │
                    │  VPN                     │
                    │  Traffic Analysis        │
                    └────────────┬─────────────┘
                                 │
                         Controller Port
                         Physical WAN jack
                                 │
                    ┌────────────▼─────────────┐
                    │       OpenWrt Router     │
                    │                          │
                    │  Ethernet switch         │
                    │  VLAN                    │
                    │  Wi-Fi AP/client         │
                    │  SSH                     │
                    │  Hardware/firmware ID    │
                    │  LEDs                    │
                    │  Diagnostics             │
                    └──────────────────────────┘


The router provides the hardware functions while the Pi provides management, computation, storage, and higher-level networking functions.

The controller is designed around generic OpenWrt compatibility. The WNR1000v2 is the eventual constrained hardware target, not the definition of the Pi software.

System Intent

The project has four major goals.

1. Extend legacy router hardware

A 4 MB flash / 32 MB RAM router can continue serving as:

managed Ethernet switch
VLAN-aware network device
managed wireless AP
Wi-Fi client
wireless-to-Ethernet adapter
travel-network radio interface

The Pi supplies the computational resources required for modern networking services.

2. Preserve OpenWrt compatibility

The Pi communicates through established OpenWrt mechanisms:

SSH
UCI
ubus
netifd
standard Linux networking interfaces
standard wireless interfaces
supported OpenWrt utilities

The Pi therefore acts as an OpenWrt secondary management layer, rather than replacing OpenWrt.

3. Provide a familiar interface

The Pi hosts a locally accessible web interface using an OpenWrt/LuCI-inspired layout:

Status
System
Network
Wireless
Switch
Diagnostics
Logs


The initial interface is read-only and displays the actual state of the connected router.

4. Establish a foundation for constrained firmware

After the generic controller has been validated against multiple OpenWrt devices, the project will produce a purpose-built WNR1000v2 image containing only the functionality required by the controller and hardware.

Router Responsibilities

The eventual 4 MB router image is centered around:

Ethernet
├── managed switch
├── VLAN support
└── Controller Port

Wireless
├── Managed AP
├── Wi-Fi client
└── live Wi-Fi scanning

Management
├── SSH
├── persistent host key
├── Pi controller key
└── OpenWrt configuration

Identity
├── immutable factory MAC
├── configurable operational MAC
├── hardware identity
└── firmware identity

Diagnostics
├── LEDs
├── switch-port state
├── interface statistics
├── Wi-Fi status
├── boot information
└── system health


The Controller Port is always the physical WAN jack.

Its logical purpose depends on deployment:

Home / AP deployment
    Controller Port → upstream/home Ethernet

Travel deployment
    Controller Port → Raspberry Pi


The physical WAN jack therefore becomes the standardized Pi connection point while retaining flexibility in the logical network design.

MAC Identity

The router maintains two MAC identities:

Factory MAC
    │
    └── immutable hardware identity

Operational MAC
    │
    └── active network identity


Normal home/AP operation:

Operational MAC = Factory MAC


Travel mode permits the Pi to configure the operational MAC.

This provides a foundation for future synthetic/randomized MAC functionality without losing predictable hardware identity.

This keeps the generic Pi controller ahead of the hardware-specific optimization work. That is important: the WNR1000v2 should ultimately become a constrained hardware endpoint for a mature controller, rather than forcing the controller architecture to be designed around the limitations of a 4 MB / 32 MB router.
